# iM 조건체크 — PRD v1.0

> **한 문장 정의:** 사전 안내 조건 V1과 최종 약정 조건 V2를 전자서명 직전에 자동 대조하고, 달라진 조건·금전적 영향·원문 근거를 고객이 확인한 뒤 그 비교 기록의 무결성까지 검증할 수 있게 하는 서비스입니다.

## 1. Executive Summary

모바일 대출에서는 사전 한도·금리 조회와 최종 심사·약정이 서로 다른 시점에 진행됩니다. 고객의 신용·소득·부채, 신청금액, 기준금리, 우대조건 충족 여부와 심사 결과에 따라 최종 조건은 정상적으로 달라질 수 있습니다. 문제는 조건이 달라지는 것 자체가 아니라 고객이 여러 화면과 문서에서 차이를 직접 찾고, 그 차이가 월 납입액과 총비용에 미치는 영향을 스스로 계산해야 한다는 점입니다.

iM 조건체크는 대출 추천이나 심사를 대신하지 않습니다. iM뱅크가 이미 보유한 사전조건과 최종조건을 동일한 Field Schema로 비교하고, 금리·기간·상환방식·우대조건·수수료 등의 변경을 서명 전에 보여줍니다.
AI는 비정형 문서의 의미 연결과 쉬운 설명을 담당하고, Rule·Calculation Engine은 비교와 금액 산출을 담당합니다.
블록체인은 당시 비교 결과와 고객 확인 기록이 이후 바뀌지 않았음을 확인하는 데만 사용합니다.

## 2. 배경과 문제 정의

### 2.1 핵심 문제

> 모바일 대출 고객은 사전조회에서 안내받은 조건과 최종 약정 조건이 무엇이 달라졌는지, 왜 달라졌는지, 그 변화가 실제 부담액에 어떤 영향을 주는지 서명 전에 한눈에 확인하기 어렵습니다.

이를 `변경 투명성 공백`으로 정의합니다.

- 사전조회, 상담, 최종 심사와 약정이 서로 다른 시점에 존재합니다.
- 사전조건과 최종조건은 정상적인 심사와 재산정으로도 달라질 수 있습니다.
- 조건은 금리뿐 아니라 우대조건, 기간, 상환방식, 중도상환수수료, 인지세 등으로 구성됩니다.
- 고객은 여러 화면·상품설명서·약정서를 오가며 차이를 찾아야 합니다.
- 금리 차이를 월 납입액과 예상 총이자로 다시 계산해야 의사결정에 사용할 수 있습니다.
- 기존의 `이해했습니다` 체크만으로는 실제 변경 내용을 이해했는지 확인하기 어렵습니다.

### 2.2 문제를 표현하는 방식

| 사용할 표현 | 피할 표현 |
| --- | --- |
| 심사와 재산정으로 조건이 달라질 수 있지만 고객은 변화와 비용 영향을 한눈에 확인하기 어렵습니다. | 은행이 안내 조건을 몰래 바꾸는 일이 빈번합니다. |
| 비대면 설명 과정에서 고객의 실질적인 이해를 지원할 장치가 필요합니다. | 대출고객 대부분이 계약 내용을 이해하지 못합니다. |
| 조건 변경 인지 실패율은 사용자 조사로 추가 검증할 제품 가설입니다. | 조건 비교 기능이 민원을 확실히 줄입니다. |

### 2.3 확인된 근거와 제품 해석

| 근거 | 확인된 사실 | 제품에 적용한 해석 |
| --- | --- | --- |
| 비대면 전환 | 금융위원회가 제시한 A은행 신용대출 비대면 판매 비중은 2019년 28.8%에서 2021년 68.5%로 증가 | 직원의 실시간 설명 없이 고객이 스스로 조건을 확인하는 상황이 증가 |
| 모바일 설명서 이용 | 비대면 금융상품 구매자의 78.9%가 모바일을 이용했고 약 40%는 설명서를 잘 읽지 않는다고 응답 | 긴 약정서와 PDF의 단순 제공만으로 실질적인 이해를 만들기 어려움 |
| 형식적 이해 확인 | 중요사항을 확인하지 않았거나 이해하지 못했지만 이해했다고 서명한 비율이 각각 38.5%, 14.5%로 총 53% | 전체 동의와 실제 이해를 같은 것으로 취급하면 안 됨 |
| 조건의 개인화 | 신용대출의 한도·상환방식·금리는 신용, 상환능력, 부채현황과 금리 구성에 따라 달라짐 | 사전값과 최종값의 차이는 정상적인 재산정에서도 발생 가능 |
| 대출 중요사항 | 금리·변동 여부, 중도상환수수료, 상환금액·이자율·시기, 고객 부담금액이 중요사항으로 제시됨 | 금리 하나가 아니라 계약 구조와 비용을 함께 비교해야 함 |
| 해외 선행 절차 | 미국 CFPB는 Closing Disclosure의 기간·금액·금리·월 납입액·비용을 최근 Loan Estimate와 확인하도록 안내 | 서명 전에 사전 안내와 최종 조건을 대조하는 절차의 필요성을 뒷받침 |

### 2.4 아직 검증이 필요한 제품 가설

- 국내 모바일 신용대출에서 사용자가 V1·V2 차이를 실제로 놓치는 빈도
- 사용자가 가장 중요하게 판단하는 변경 항목의 순서
- 원화 비용 변화가 Percentage Point보다 계약 판단에 더 직접적인 도움을 주는지
- 비교 화면이 약정 흐름을 방해하지 않으면서 이해도를 높이는지
- 무결성 검증 영수증이 실제 신뢰와 사후 확인 의향을 높이는지

## 3. Target User와 Job To Be Done

### 3.1 Primary Target

연령이나 소득이 아니라 이용 상황으로 타깃을 정의합니다.

| 구분 | 정의 |
| --- | --- |
| 필수 행동 | iM뱅크에서 개인 신용대출 사전 한도·금리 조회를 완료하고 해당 조건으로 신청한 고객 |
| 이용 시점 | 최종 심사가 완료되고 서명 대상 전자약정서가 생성된 직후 |
| 경험 수준 | 대출을 처음 이용하거나 계약조건을 반복적으로 비교하는 데 익숙하지 않은 저빈도 이용자 |
| 주요 불안 | 처음 본 금리와 현재 금리가 같은지, 월 부담과 총이자가 얼마나 달라졌는지 확신하기 어려움 |
| 원하는 결과 | 30초 안에 중요한 변경을 확인하고 진행·재검토·상담 중 하나를 선택 |

### 3.2 Job To Be Done

> 최종 대출계약에 서명하려는 순간, 처음 안내받은 조건과 달라진 내용을 금액과 근거로 확인해 현재 조건으로 계약을 진행할지 스스로 결정하고 싶습니다.

### 3.3 Secondary User

- 대출 상담원: 고객이 문의한 변경 항목·Reason Code·원문 근거를 같은 Case 기준으로 확인합니다.
- 소비자보호·준법 담당자: 어떤 조건을 언제 설명했고 고객이 무엇을 확인했는지 감사 가능한 기록으로 확인합니다.
- 운영자: AI 추출 실패, 출처 충돌, 계산 불일치와 Proof Anchor 지연을 관리합니다.

## 4. Product Vision과 가치 제안

### 4.1 Product Vision

> 고객이 약정서를 전부 다시 읽지 않아도 달라진 조건을 먼저 이해하고, 은행은 어떤 조건을 어떻게 설명했는지 일관되게 증명할 수 있는 서명 전 검증 단계가 됩니다.

### 4.2 고객 가치

1. 변경된 조건만 먼저 보여줘 계약서를 처음부터 다시 읽는 부담을 줄입니다.
2. 금리 차이를 월 납입액과 예상 총이자로 변환합니다.
3. 변경 사유와 약정서 근거 위치를 함께 제공해 AI 설명을 원문으로 확인할 수 있게 합니다.
4. 유리한 변경, 불리한 변경, 구조 변경, 분석 불확실을 구분합니다.
5. 진행·재검토·상담 중 고객이 직접 다음 행동을 선택합니다.
6. 당시 비교 결과와 확인 기록을 사후에 다시 검증할 수 있습니다.

### 4.3 은행 가치

- 설명의무를 문서 제공에서 조건별 확인 과정으로 구체화합니다.
- 사전 안내, 최종약정, 고객 확인 이력을 하나의 Case로 연결합니다.
- 상담원에게 고객 문의 맥락과 근거를 함께 전달합니다.
- 설명 관련 민원과 감사 대응 시 동일한 Version의 자료를 재현할 수 있습니다.
- 대출 핵심 거래 흐름 안에 AI와 검증 인프라를 적용한 고객 접점을 확보합니다.

## 5. 목표와 비목표

### 5.1 Product Goals

- 사전조건 V1과 최종조건 V2를 동일 Field Code로 비교합니다.
- 불리한 변경과 구조 변경을 서명 전에 우선 노출합니다.
- 금리·기간 변화의 월 납입액과 예상 총이자 영향을 계산합니다.
- 모든 설명에 확인 가능한 원문 또는 Reason Code를 연결합니다.
- 불확실한 항목을 `변경 없음`으로 표시하는 False Safe를 방지합니다.
- 고객의 확인과 선택을 Version과 함께 기록합니다.
- 비교 결과의 무결성을 재검증할 수 있게 합니다.

### 5.2 Non-goals

- 대출상품 추천과 금융사 간 예상 한도·금리 비교
- 대출 승인·거절, 신용평가, 한도 결정과 금리 산정
- 계약의 법적 유효성 판단과 고객 대신 계약 적합성 결정
- 전세·주택담보·사업자대출의 담보·등기·보증 검증
- 실제 자금 실행과 실계좌 연동
- 계약서 원문·개인정보·금융값의 On-chain 저장
- 범용 AI 금융상담 챗봇
- 안심클로징 및 ProofTalk 기능의 통합
- 기술 스택과 공급자 선정
- 일정 또는 15일 단위 작업 분해

## 6. 경쟁 범위와 차별점

### 6.1 경쟁 범위 정의

iM 조건체크의 경쟁 대상은 하나의 동일 제품만이 아니라 고객이 현재 문제를 해결하는 여러 대체수단입니다.

| 유형 | 현재 제공 가치 | iM 조건체크의 차이 |
| --- | --- | --- |
| 대출 비교 플랫폼 | 여러 금융사의 예상 한도·금리·상품을 비교 | 한 금융기관 안에서 고객이 실제 신청한 V1과 서명할 V2의 Version 차이를 검증 |
| 은행 사전조회·상품설명 | 현재 예상 조건과 상품 구조를 안내 | 사전조회 값을 불변 Snapshot으로 남기고 최종 약정과 자동 연결 |
| AI 금융상담 | 질문에 답하고 상품·약관을 설명 | 대화가 아니라 두 시점의 공식값·비용·근거를 하나의 검증 단위로 생성 |
| 전자약정 | 최종 계약서 제시와 동의·서명 기록 | 서명 전에 이전 안내와 달라진 항목을 독립 단계로 확인 |
| 전자문서·블록체인 증명 | 문서 발급주체와 위·변조 여부를 검증 | 문서뿐 아니라 V1·V2 비교 결과와 고객 확인 시점까지 연결 |
| 수기 비교 | 사용자가 과거 화면·문서와 최종 약정서를 직접 대조 | Field Mapping, 계산과 우선순위를 자동화 |

### 6.2 주요 비교 서비스

- **대출 비교 플랫폼:** 네이버페이 등의 대출비교는 여러 제휴 금융사의 대출 가능 조건을 비교하는 탐색·중개 단계에 가깝습니다. iM 조건체크는 금융사 선택 이후 실제 신청건의 사전조건과 최종 약정조건을 비교합니다.
- **은행 상품 화면과 계산기:** 현재 상품의 금리·상환방식·비용을 이해하는 데 도움을 주지만 과거 Snapshot과 최종 계약 Version의 자동 Diff가 핵심은 아닙니다.
- **CFPB Loan Estimate·Closing Disclosure:** 사전 견적과 최종 공시를 비교하는 해외 제도적 선행 구조입니다. iM 조건체크는 이 비교 행위를 국내 모바일 신용대출 흐름에서 자동화한다는 제품 가설입니다.

공개 자료만으로 국내 모든 은행 앱에 동일 기능이 없다고 단정하지 않습니다. 경쟁 우위는 실제 App Audit에서 `V1 저장`, `V2 자동 Diff`, `비용 영향`, `근거`, `고객 확인`, `무결성 검증` 여섯 항목으로 재검증합니다.

### 6.3 ProofTalk(가상AI상담 서비스)와의 차이

| 구분 | ProofTalk(가상AI상담 서비스) | iM 조건체크 |
| --- | --- | --- |
| 핵심 문제 | AI 상담 답변의 근거와 사후 신뢰 | 사전 안내와 최종 약정 사이의 변경 투명성 |
| Primary Moment | 대출 상담 중 | 최종 전자서명 직전 |
| 핵심 입력 | 질문, 상담 답변, 상품문서 | 공식 V1 Snapshot, V2 Snapshot, 최종 약정서 |
| 핵심 출력 | 근거가 연결된 상담 답변 | Before·After·Delta·비용·Reason·Evidence |
| 계산 | 답변 보조 또는 예시 계산 | 계약값 기반 월 납입액·총이자의 결정론적 재계산 |
| 고객 행동 | 추가 질문과 상담 지속 | 진행·재검토·상담 선택 |
| 증명 대상 | 어떤 질문에 어떤 답변과 근거가 제공됐는지 | 어떤 조건을 안내받고 어떤 최종조건과 비교했으며 무엇을 확인했는지 |

두 서비스 모두 `근거 있는 AI`와 `변조 방지 기록`을 사용하지만 Product Object와 Moment가 다릅니다. ProofTalk는 `대화의 신뢰`, iM 조건체크는 `계약 Version의 일치와 변경 이해`를 다룹니다.

### 6.4 핵심 차별화 문장

> 여러 금융사의 예상 조건을 비교하거나 최종 문서를 단순 설명하는 것이 아니라, 동일 신청건의 사전조건과 최종 서명조건을 표준 Schema로 자동 대조하고 비용 영향·원문 근거·고객 확인·검증 기록을 하나의 서명 전 흐름으로 연결합니다.

### 6.5 차별화 구성요소

1. **두 시점:** V1 사전조건과 V2 최종약정
2. **동일 Schema:** 원문 문구가 아닌 표준 Field Code 비교
3. **비용 번역:** Percentage Point를 월 납입액·예상 총이자로 변환
4. **Grounded Evidence:** Reason Code와 약정서 Source Span 연결
5. **Informed Decision:** 불리·구조 변경의 확인 후 진행
6. **Proof:** Comparison·Decision Version의 무결성 검증

## 11. AI 역할과 필요도

### 11.1 AI 필요도: 8/10

AI는 제품의 차별적인 자동화와 설명 경험에 중요하지만 최종 판단기관은 아닙니다. 모든 입력이 완전히 구조화돼 있다면 비교와 계산은 AI 없이도 가능하므로 10점으로 평가하지 않습니다. 실제 은행 문서의 표·문장·조건 표현이 비정형이고 고객에게 쉬운 설명이 필요하다는 점에서 8점으로 판단합니다.

| AI가 수행 | AI가 수행하지 않음 |
| --- | --- |
| 비정형 약정서에서 조건 후보와 단위 추출 | 대출 승인·거절 |
| 다른 문구를 표준 Field Code로 Semantic Mapping | 한도·금리 산정 |
| 문서 Page·Block·Source Span 반환 | 월 납입액·총이자 최종 계산 |
| 확인된 Reason Code와 Evidence의 쉬운 설명 | 변경의 유불리 최종 판정 |
| 추출 불확실성과 누락 사유 반환 | 근거 없는 변경 원인 추정 |
| 고객 질문의 근거 문서 탐색 보조 | 계약 적합성·법적 유효성 판단 |

### 11.2 AI가 필요한 이유

1. 약정서와 상품설명서는 같은 조건도 서로 다른 문구와 표 구조로 표현됩니다.
2. 모든 조건이 구조화 API로 제공되지 않을 수 있습니다.
3. 고객은 `가산금리 재산정`보다 무엇이 왜 달라졌는지 짧은 설명을 필요로 합니다.
4. Evidence 위치를 함께 반환하면 긴 문서에서 근거를 빠르게 찾을 수 있습니다.

### 11.3 필요한 정도와 안전 경계

- 구조화 API 값이 있으면 AI보다 API를 우선합니다.
- 숫자·날짜는 Source Span에서 같은 값이 검증돼야 합니다.
- 중요값 Confidence가 기준 미만이면 자동 확정하지 않습니다.
- AI는 값을 계산하거나 유불리를 최종 판정하지 않습니다.
- Reason Code나 문서 근거가 없으면 원인을 생성하지 않습니다.
- AI 장애가 전체 대출시스템 장애로 전파되지 않도록 원문·상담 Fallback을 제공합니다.

## 12. 블록체인 역할과 필요도

### 12.1 블록체인 필요도: 6/10 — 은행 단독 MVP 기준

블록체인은 제품의 핵심 고객가치인 `변경 발견과 비용 이해`를 직접 만들지는 않습니다. 은행 내부 단일 시스템에서는 전자서명, Append-only Audit Log와 위·변조 방지 저장소로도 상당 부분 구현할 수 있으므로 10점 만점에 6점으로 평가합니다.

다만 향후 대출비교 플랫폼, 은행, 보증기관, 감독·분쟁조정 주체가 동일 기록을 독립 검증하는 구조에서는 필요도가 8/10까지 올라갑니다. 공모전 MVP에서는 네트워크 자체보다 `누가 어떤 기록을 독립 검증하는가`와 `개인정보를 올리지 않는 경계`를 보여주는 수준이 적절합니다.

### 12.2 블록체인이 수행하는 역할

- 고객에게 어떤 V1 조건이 언제 안내됐는지 검증
- 어떤 V2와 비교했는지 검증
- 어떤 Comparison 결과가 표시됐는지 검증
- 고객이 어떤 변경을 확인하고 어떤 결정을 했는지 검증
- 기록 이후 Hash가 변경되지 않았는지 검증

### 12.3 블록체인이 수행하지 않는 역할

- 계약 조건이 고객에게 좋은지 판단
- 약정서 내용이 법적으로 옳거나 사실인지 보증
- AI 추출값의 정확성 판단
- 개인정보·대출금액·금리·계약서 원문 저장
- 대출 승인과 전자서명 대체

### 12.4 On-chain과 Off-chain 경계

| Off-chain | On-chain 또는 검증 원장 |
| --- | --- |
| 계약서·설명서 원문 | 비식별 Record ID |
| 대출금액·금리·신용정보·고객정보 | Canonical Payload Hash |
| Comparison Item 전체 | Schema·Policy Version |
| AI Prompt·Output·Evidence Text | Issuer 식별자 |
| Decision·전자서명 원문 | Recorded Timestamp |

### 12.5 구현 수준

MVP에서 반드시 보여줘야 하는 범위는 다음과 같습니다.

1. V1·V2·Comparison·Decision을 Canonical JSON으로 변환합니다.
2. 각 Hash와 정책 Version을 묶어 Proof Payload를 생성합니다.
3. 원장에는 Payload 원문이 아닌 Hash와 최소 Metadata만 기록합니다.
4. 검증 시 Off-chain Payload로 Hash를 재계산하고 원장값과 대조합니다.
5. 원장 장애는 계약 완료를 실패로 바꾸지 않고 비동기로 재시도합니다.

## 14. 핵심 정책

### 14.1 Overall Status

```
if any required item is UNKNOWN:
  UNCERTAIN
else if any item is WORSE or STRUCTURAL_CHANGE:
  CHECK_REQUIRED
else if any item is BETTER and all other items are SAME or BETTER:
  BURDEN_DECREASE
else if all items are SAME:
  NO_CHANGE
else:
  UNCERTAIN
```

### 14.2 필수 확인

```
requiredReviewItems =
  contributesToOverall == true
  and itemStatus in [WORSE, STRUCTURAL_CHANGE, UNKNOWN]
```

### 14.3 비용 표시

```
monthlyPaymentDelta = V2 monthly payment - V1 monthly payment
totalInterestDelta = V2 total interest - V1 total interest
fixedFeeDelta = V2 fixed fees - V1 fixed fees
totalCostDelta = totalInterestDelta + fixedFeeDelta
```

- 월 납입액 Delta와 대출원금 Delta는 총비용에 가산하지 않습니다.
- 중도상환수수료와 연체이자는 미래 행동·기간이 없어 금액 합계에서 제외합니다.
- 변동금리는 미래 금리를 예측하지 않고 동일한 현재금리 유지 가정으로만 계산합니다.

## 15. 데이터·보안 원칙

- 고객 API는 기존 은행 인증 Session과 Application 소유권을 확인합니다.
- 계약서 원문과 추출 Text는 암호화 저장합니다.
- AI 입력 전 주민등록번호·계좌번호·전화번호·성명 등 PII를 Masking합니다.
- 필요한 문서 Block만 AI에 전달합니다.
- 고객 금융값과 원문을 Application Log와 Analytics에 저장하지 않습니다.
- 원문은 인증 후 짧은 만료시간의 Signed URL로 제공합니다.
- Snapshot 생성, 비교, Review, Decision, Anchor, Verify는 Append-only Audit Event로 남깁니다.
- V1·V2 Snapshot은 수정하지 않고 새 Version만 생성합니다.

| Ledger 장애 | 약정 완료 유지, 비동기 재시도 | 조건 확인 기록을 처리하고 있습니다. |
| Hash 불일치 | 검증 실패와 운영 Alert | 기록의 무결성을 확인할 수 없습니다. |

## 19. Risk와 대응

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| 조건 변경 빈도가 낮음 | 고객이 기능 필요성을 느끼지 못함 | 금리뿐 아니라 우대조건·기간·수수료까지 포함하고 실제 Case 빈도 검증 |
| AI 숫자 오인식 | 잘못된 계약 판단 유발 | 구조화 API 우선, Source Span Exact Match, Confidence Gate |
| 변경 사유 Hallucination | 은행 설명 신뢰 훼손 | Reason Code·승인 근거가 없으면 사유 생성 금지 |
| 계산값과 실제 상환액 차이 | 고객 오해 | 은행 계산 규칙 검증, 계산 가정 표시, 변동금리·일할이자 한계 명시 |
| 약정 흐름 방해 | 이탈 증가 | NO_CHANGE는 한 화면으로 축약, 불리·구조 변경만 필수 Review |
| 블록체인 장식화 | 기술 필요성 약화 | 은행 단독 대체수단과 다기관 검증 확장 시나리오를 명확히 구분 |
| 법률판단으로 오인 | 책임 범위 혼동 | 사실 비교·예상 영향만 제공하고 최종 결정 주체를 고객으로 명시 |
| Version 연결 오류 | 다른 견적과 계약 비교 | Application ID·상품·고객·시점·문서 Hash 선행 검증 |

## 20. Release Acceptance Criteria

- [ ] V1과 V2가 수정 불가능한 Snapshot으로 저장됩니다.
- [ ] 신청 당시 유효했던 V1을 역사적 기준으로 정확히 비교합니다.
- [ ] V2와 서명 약정서 Version이 약정 직전 다시 검증됩니다.
- [ ] 모든 필수 Field가 동일 Schema와 단위로 정규화됩니다.
- [ ] 구조화 API와 약정서 충돌이 `UNCERTAIN`으로 전파됩니다.
- [ ] 원리금균등 계산의 마지막 회차 잔액이 0원입니다.
- [ ] 월 납입액·원금·조건부 비용이 총비용에 중복 집계되지 않습니다.
- [ ] 필수 변경 미확인 상태에서는 PROCEED가 활성화되지 않습니다.
- [ ] Reason Code가 없을 때 AI가 원인을 생성하지 않습니다.
- [ ] False Safe가 0건입니다.
- [ ] Decision 저장 전 계약 API가 호출되지 않습니다.
- [ ] Ledger 장애가 계약 완료를 실패로 바꾸지 않습니다.
- [ ] On-chain Payload와 Analytics에 개인정보·원문·금융값이 포함되지 않습니다.
- [ ] 같은 입력과 정책 Version으로 동일 Comparison Hash가 생성됩니다.
- [ ] 변경 상태와 방향을 색상 없이도 이해할 수 있습니다.
